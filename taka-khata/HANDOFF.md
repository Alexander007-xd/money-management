## Notes for next session
- `db.ts` exports the `db` singleton for app/repo use and `TakaKhataDatabase` whose constructor accepts a database name, so tests can use an isolated DB (`new TakaKhataDatabase('test-name')`) and delete it afterwards with `Dexie.delete(name)`. `db.test.ts` does exactly that.
- Default category seeding is tied to database creation (`populate`), not to every open. Reopening or a second instance keeps exactly 9 rows. If the categories table is emptied manually, defaults are not re-seeded.
- `settings` is typed as `Setting { key: string; value: string | number }` using the `key` primary key from Schema.md.
- Calc semantics: `balance` all-time; month filtering via `monthKey(date)`; percentages rounded and may sum to 99/101; `expenseByCategory` skips null categories and returns `[]` when nothing was spent.
- Validation API is result objects `{ ok, value/errors }` with stable codes; `validateAmountInput(raw)` handles raw form text; ids are any non-empty string.
- Repo transaction API (2.2): every function takes an optional last `database` argument defaulting to the `db` singleton, so tests pass an isolated `TakaKhataDatabase`. `addTransaction(input)` generates `id` with `crypto.randomUUID()` and both timestamps; `updateTransaction(id, input)` keeps the original `createdAt` and sets a new `updatedAt`; `deleteTransaction(id)` is a permanent delete; `restoreTransaction(snapshot)` re-adds a deleted record and throws `StorageError` if that id already exists.
- Repo errors: `ValidationError` (exported from `repo.ts`) carries the same `{ field, code }[]` from `validate.ts`; `StorageError` wraps any Dexie failure. Updating a missing id throws `StorageError`. There is no `getTransaction` helper yet (not in TRD.md); EditEntry can use `listTransactions` until one is needed.
- `listTransactions` returns newest first by `date`, then `createdAt`, then `id`; filters are `{ month: 'YYYY-MM', type, categoryId }`, validated, and can be combined. Month uses the `date` index or the `[type+date]` compound index, then an in-memory check for the remaining filters.
- Repo categories/cash checks/settings (2.3): `getCategories()` returns every category (archived included) sorted by `sortOrder` then `id`; screens filter `archived` for pickers. `addCategory({ nameEn, nameBn, icon })` creates a non-default, visible category with the next `sortOrder`. `updateCategory(id, changes)` accepts only `nameEn`, `nameBn`, `icon`, `archived`; it keeps `isDefault` and `sortOrder`, so a default category can be renamed or hidden but never deleted or made non-default. There is deliberately no `deleteCategory` (not in TRD.md/PRD.md).
- `addCashCheck({ date, countedMinor, expectedMinor })` computes `diffMinor` with `calc.diffForCheck`; `listCashChecks()` returns newest first by `date`, then `createdAt`, then `id` with no limit (the CashCheck screen can slice the last 5).
- `getSetting(key)` returns `value | undefined`; `setSetting(key, value)` upserts. `language` must be `'bn' | 'en'`, `schemaVersion` must be an integer >= 1; other keys accept a string or number.
- Backup (2.4): `exportAll()` returns `{ app: 'taka-khata', schemaVersion: DB_VERSION, exportedAt: Date.now(), transactions, categories, cashChecks, settings }` (arrays straight from the tables). `importAll(unknown)` first runs `validateBackup(input, DB_VERSION)` from `validate.ts` (rejects wrong `app`, newer schema, bad `exportedAt`, missing/non-array tables, and every invalid record; record errors are prefixed like `transactions[0].amountMinor`), then clears and bulk-adds all four tables inside one Dexie `rw` transaction. A write failure (for example duplicate ids) aborts the transaction and is rethrown as `StorageError`, leaving the old data intact.
- `BackupData` and `BACKUP_APP` live in `types.ts`; `validateSetting` and `validateBackup` are pure and live in `validate.ts`. `exportAll`/`importAll` take the optional last `database` argument like the other repo functions.
- Machines (3.1): reducers are pure and return only the next state; navigation, repo calls, toasts, timers and dialogs stay in screens. Event unions are exported from `machines.ts` (`FormEvent`, `DeleteEvent`, `CheckEvent`, `ImportEvent`). Unknown/inapplicable events return the current state. `formReducer` covers open/save/valid/invalid/success/failure/retry/back/discard; `deleteReducer` maps both Undo and the 5 s timeout from `deleted` back to `idle` (the screen decides whether to restore or permanently delete); `checkReducer` is only `input <-> result`; `importReducer` covers parse/confirm/import/done/error.
- `routeAfterSave(mode)` with `'add' | 'edit'` returns `ROUTES.home` or `ROUTES.history` for the form table's saved row. `checkOutcome(diffMinor)` returns `matches | less | more` for the three CashCheck result rows. The CashCheck screen still builds the prefilled routes and uses `diffForCheck` from `calc.ts`.
- Rules deliberately not added (not in docs): source/name length caps, `countedMinor >= 0`, future cash-check dates, UUID-only ids.
- i18n (3.2): import `t` from `src/i18n/translate.ts` in pure modules, or `useLanguage()` from `src/i18n/index.ts` in components. `t` replaces `{name}` placeholders; numeric params go through `formatNumber`, string params are inserted unchanged. `formatNumber(value, lang)` converts both directions and leaves non-digits alone. `LanguageProvider` defaults to `bn`, accepts an optional `initialLang`, and keeps `document.documentElement.lang` in sync. `money.ts` imports only `src/i18n/format.ts`, so it stays free of React.
- `formatDay(date, lang)` keeps its signature but now reads `day.today`, `day.yesterday` and `month.1`..`month.12` from i18n. `formatMoney` keeps its signature and uses `formatNumber`.
- App shell (3.3): `App` treats `undefined` as "still loading", `null` as "no language saved", and `'bn' | 'en'` as saved. While loading it renders an empty `.app` with `aria-busy`; if `getSetting` fails it shows `error.storageUnavailable`.
